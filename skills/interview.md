# interview

Confidence before keystrokes. The rule here is 95%: if you are not that sure
what to build, ask — but ask *once*, well.

1. **Read everything first** — the brief, the code it touches, the docs it
   mentions. Most questions answer themselves in the codebase.
2. **Do everything that does not depend on the answer.** Never block a whole
   task on one open question.
3. **Ask only where two readings lead to genuinely different work.** "Should I
   use tabs" is not that question.
4. **Offer your recommendation as the first option.** A question with no
   default makes the sovereign do your thinking.
5. **State assumptions out loud** for anything you decided yourself.

Then write the plan before the code: what changes, in what order, and how you
will know it worked.
